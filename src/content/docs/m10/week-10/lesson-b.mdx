## try … on error

`try {body} on error {message} {handler}` runs the body. If all goes well, the handler is skipped. If a command in the body raises an error, the body stops at once, the error message goes into `message`, and the handler runs. Either way, the script carries on after the `try`.

It does the same job as `if {[catch …]}`, but it reads like a sentence, and you cannot mix up 0 and 1.

<Diagram name="w10-try-paths" alt="A flow diagram. try with its body runs the risky commands. With no error, the rest of the body runs and the on error part is skipped. With an error, the body stops at once and on error with the variable message and its handler runs; message holds the error message. Both paths then meet at finally with its clean-up code, which runs at the end after an error or after a normal run." />

<WorkedExample
  code={`proc blockArea {w h} {
    if {$w <= 0} {
        error "width must be positive, got $w"
    }
    return [expr {$w * $h}]
}
foreach size {{120 80} {0 10} {100 80}} {
    try {
        set area [blockArea [lindex $size 0] [lindex $size 1]]
        puts "area $area um2"
    } on error {message} {
        puts "skipped: $message"
    }
}
puts "report done"`}
  notes={{
    1: 'Lesson A’s proc: it raises an error for a width that is not positive.',
    7: 'Three blocks; the second has a width of 0.',
    8: 'The risky part goes in the body of try.',
    9: 'For the bad block, blockArea raises an error here, so the next line is skipped.',
    10: 'Output: area 9600 um2, then area 8000 um2 for the last block.',
    11: 'On an error, the message goes into the variable message.',

## finally: always runs

Add `finally {…}` at the end of a `try`, and its code runs every time: after a normal run, and after an error too. Use it for work that must happen whatever the result, like counting how many blocks you have checked, or, from Week 12, closing a file.

<TclPlayground client:visible code={`foreach w {5 0} {
    try {
        if {$w <= 0} {
            error "bad width $w"
        }
        puts "width $w ok"
    } on error {message} {
        puts "skipped: $message"
    } finally {
        puts "done with $w"
    }
}`} />

## Defensive procs

A defensive proc checks its input at the door. Its first lines are <GlossaryTerm term="guard-clause">guard clauses</GlossaryTerm>: is the number of values right, is each value a number, does it make sense? Each failed check raises an error that says what is wrong and shows the value. After the guards, the rest of the proc can trust its input.

To test "is this text a number?", use `string is double -strict $value`: 1 for `12`, `-5` or `2.5`, and 0 for `ten`. Without `-strict`, an empty text counts as a number too (see the traps).

<WorkedExample
  code={`proc checkRect {rect} {
    if {[llength $rect] != 4} {
        error "a rectangle has 4 numbers, this one has [llength $rect]"
    }
    foreach value $rect {
        if {![string is double -strict $value]} {
            error "not a number: $value"
        }
    }
    if {[lindex $rect 2] <= [lindex $rect 0]} {
        error "x2 must be larger than x1"
    }
    return ""
}
foreach rect {{20 20 220 180} {20 20 220} {20 20 two 180} {220 20 20 180}} {
    try {
        checkRect $rect
        puts "ok: $rect"
    } on error {message} {
        puts "bad: $message"
    }
}`}
  notes={{
    1: 'A proc that only checks: it returns nothing for a good rectangle.',
    2: 'Guard 1: the number of values (Week 5).',
    3: 'Say what is wrong, and show what you got.',
    5: 'Guard 2: every value must be a number.',
    6: '! turns 1 into 0 and 0 into 1: "if it is NOT a number".',
    7: 'Show the bad value in the message.',
    10: 'Guard 3: the rectangle must make sense.',
    13: 'All guards passed.',
    15: 'Four rectangles: one good, then three different mistakes.',
    17: 'If checkRect raises an error, the next line is skipped.',
    18: 'Output: ok: 20 20 220 180',
    20: 'Output: bad: a rectangle has 4 numbers, this one has 3, then bad: not a number: two, then bad: x2 must be larger than x1'
  }}
/>

## Common traps

<Trap
  wrong={`set w ""
if {[string is double $w]} {
    puts "a number"
} else {
    puts "not a number"
}`}
  output={`a number`}
  fix={`set w ""
if {[string is double -strict $w]} {
    puts "a number"
} else {
    puts "not a number"
}`}
  why="Without -strict, string is says 1 for an empty text, so a forgotten value slips through your guard. Always write -strict in a guard clause."
/>

<Trap
  wrong={`proc blockArea {w h} {
    if {$w <= 0} {
        error "width must be positive, got $w"
    }
    return [expr {$w * $h}]
}
foreach w {120 0 100} {
    puts "area [blockArea $w 80] um2"
}`}
  error={`width must be positive, got 0`}
  fix={`proc blockArea {w h} {
    if {$w <= 0} {
        error "width must be positive, got $w"
    }
    return [expr {$w * $h}]
}
foreach w {120 0 100} {
    try {
        puts "area [blockArea $w 80] um2"
    } on error {message} {
        puts "skipped: $message"
    }
}`}
  why="The proc refuses the bad width, which is right. But nobody catches the error, so it stops the whole loop: the first block is reported, the last one never is. Put the call inside try … on error."
/>

<Trap
  wrong={`proc checkBlock {block} {
    if {[llength $block] != 5} {
        error "wrong number of values"
    }
}
foreach b {{CORE 20 20 200 160} {FUSE 10 10 20}} {
    catch {checkBlock $b}
    puts "[lindex $b 0]: fine"
}`}
  output={`CORE: fine
FUSE: fine`}
  fix={`proc checkBlock {block} {
    if {[llength $block] != 5} {
        error "wrong number of values"
    }
}
foreach b {{CORE 20 20 200 160} {FUSE 10 10 20}} {
    if {[catch {checkBlock $b} message]} {
        puts "[lindex $b 0]: $message"
    } else {
        puts "[lindex $b 0]: fine"
    }
}`}
  why="This is called swallowing an error. catch stops the error, but the script ignores what catch gives back, so every block looks fine, even FUSE with its missing value. A hidden error is worse than a crash: nobody knows to fix it. Always look at catch's result, or use try … on error."
/>
